# Make/CMake/Ninja/Cargo/Python/curl 六工具现场赛模拟题适配与验收指南

本文记录 ScintillaOS 为官方 2026 双架构镜像中的 GNU Make、CMake、Ninja、Cargo、Python 3.13 和 curl 所做的兼容适配，并给出一套可重复、可审计的现场赛模拟题。目标不是让六条 `--version` 命令勉强启动，而是让未经修改的原版程序在客体中创建工程、并行编译、链接、运行测试、访问 SQLite、创建虚拟环境、校验证书下载 HTTPS 内容，并产生可由宿主独立观察的网络副作用。

本文对应分支为 `on-site-toolchain-compat`。六工具工作建立在 Python 3.13 适配提交 `b11614e` 之上；该提交之前已有的通用 Linux ABI、VFS、Ext4、SMP 和网络能力仍然是本题的基础。运行日志和 qcow2 覆盖层位于被 Git 忽略的 `artifacts/onsite-toolchain/`，不提交官方镜像、覆盖层或认证信息。

## 1. 模拟题定义

### 1.1 题目背景

主办方提供 RISC-V64 与 LoongArch64 的 Ext4 用户态镜像，镜像已经包含六个原版工具以及 GCC、glibc、Rust 工具链、CA 证书和依赖库。参赛者不得修改六工具二进制来绕过错误，也不得在内核中按进程名伪造返回值；需要补齐操作系统对 Linux ABI、文件系统、进程、信号、时间和网络的兼容性。

### 1.2 建议题面

> 在参赛操作系统上挂载官方 Ext4 镜像并进入其根目录，完成以下任务：
>
> 1. 加载 GNU Make、CMake、Ninja、Cargo、Python 3 和 curl，并输出有效版本；
> 2. 使用 Make 并行编译两份 C 源码，链接并运行程序；验证未修改目标不会持续重建，修改源码后会重建；
> 3. 分别使用 CMake 的 `Unix Makefiles` 和 `Ninja` 生成器配置、构建并通过 CTest；
> 4. 直接使用 Ninja 构建和运行 C 工程；
> 5. 使用 Cargo 离线创建项目、完成 release 构建、运行、单元测试和 metadata 查询；
> 6. 使用 Python 完成 JSON/gzip/SHA-256、SQLite 持久化、四线程同步和 `venv --without-pip`；
> 7. 使用 curl 通过系统 CA 校验下载固定 HTTPS 内容，验证 SHA-256，并向指定服务 POST 唯一回执；
> 8. 在一个顶层 Makefile 中组合 Python 代码生成、CMake+Ninja C 构建和 Cargo Rust 构建，两个产物均需运行并输出正确结果。

## 4. 实测发现的兼容性问题

### 4.1 Ninja 调用 `rt_sigpending` 返回 `ENOSYS`

#### 现象

直接运行 `ninja -j4` 时，每完成一个子命令都会输出：

```text
ninja: sigpending: Function not implemented
```

构建有时仍能继续，但这说明 Ninja 的信号状态检查没有获得 Linux 语义，不能作为完整兼容通过。

#### 根因

`os/src/syscall/process.rs` 已存在 `sys_rt_sigpending` 实现，但 `os/src/syscall/mod.rs` 没有定义 asm-generic syscall 号 136，也没有分发到该实现。因此函数存在并不等于用户态可调用，任何原版程序都会收到 `ENOSYS`。

#### 修复

新增：

```text
SYSCALL_RT_SIGPENDING = 136
136 → sys_rt_sigpending(set, sigsetsize)
```

同时按当前 64 位信号集 ABI 校验 `sigsetsize == sizeof(u64)`：长度错误返回 `EINVAL`，空或不可写用户指针返回 `EFAULT`，正常调用把任务的 pending signal 位图安全复制到用户空间。

这是通用信号 ABI，不包含 Ninja 进程名或命令行判断。修复后 RV4、RV8 和 LA12 的直接 Ninja/CMake-Ninja 构建均不再出现 `sigpending` 错误。

### 4.2 新建 Ext4 inode 时间戳为 Epoch 0

#### 现象

修复信号后，Ninja 首轮构建成功，但第二次仍解释为：

```text
ninja explain: recorded mtime of main.o older than most recent input src/main.c (1 vs ...)
```

这里的 `1` 是 Ninja 为“存在但 mtime 为零”保留的值。Make/CMake 能完成构建不代表该元数据语义正确；持续把目标判断为陈旧会破坏增量构建效率，并可能在更复杂依赖图中引发错误。

#### 根因

项目为并发安全和属性创建新增了 `ext4_create_at_with_attrs`。该底层接口分配 inode、设置类型/权限/uid/gid，却把 atime、mtime、ctime 留为零；`VfsSuperBlock::create_file` 返回给 dentry 的 `InodeInfo` 也显式写了三个零。应用若在第一次可靠数据时间更新前查询新文件，就会看到 1970 年时间。

#### 修复

`os/src/fs/vfs.rs::VfsSuperBlock::create_file` 在创建发布事务内取得内核 realtime 秒值，并完成三层同步：

1. 新 `InodeInfo` 的 atime/mtime/ctime 使用当前时间；
2. 通过 lwext4 的 `ext4_atime_set`、`ext4_mtime_set`、`ext4_ctime_set` 持久化到 raw inode；
3. 更新路径时间缓存，使同一时刻的新旧 dentry 观察一致。

修复适用于所有普通文件和目录创建，不依赖 Make、Ninja 或文件扩展名。它也避免 qcow2 重开后时间重新变零。

### 4.3 当前 Ext4 时间分辨率边界

当前 VFS `Kstat` 只从 lwext4 的秒字段填充时间，纳秒字段为 0。因此高度并行的“编译对象→链接→生成运行结果”若正好跨过秒边界，Ninja 可能保守补建一个后继目标。修复后的关键区别是：

- 不再出现 Epoch 0/`mtime=1`；
- 补建后的目标时间有效；
- 紧接着的检查会稳定，不持续重编译链接目标；
- 构建结果和运行结果始终正确。

工作负载在观察到一次秒级补建时输出 `NINJA_COARSE_MTIME_REBUILD_OBSERVED`，但仍要求链接产物在下一次调用中不再改变。该标记是已知分辨率说明，不是“纳秒级 Ext4 已实现”的声明。若未来把 lwext4 extra timestamp 字段接入 `Kstat`，应收紧测试，要求第一次 no-op 即输出 `ninja: no work to do.`。

## 5. 六工具依赖的既有适配

本轮新增的直接内核修复只有上述两类，但六工具能够完成真实工作依赖此前已经实现并再次回归的通用能力。

本文的 `python` 段选择 SQLite 持久化、四线程和 venv 作为六工具组合中的代表负载；更完整的 Python 专项验收仍由 `scripts/verify_onsite_python.py` 负责。

### 5.4 curl

## 9. 故障排查

| 现象 | 首查 | 含义/处理 |
|---|---|---|
| `sigpending: Function not implemented` | 当前内核是否含 syscall 136 分发 | 运行了旧内核或分发修复回退 |
| Ninja 显示 mtime `1` | 新建 inode 三个时间字段 | Epoch 0 修复回退，不是正常秒级补建 |
| `NINJA_COARSE_MTIME_REBUILD_OBSERVED` | 后续是否停止改变链接产物 | 当前秒级分辨率边界；持续重建才失败 |
| Cargo 卡在下载 | `CARGO_NET_OFFLINE=true`、工程是否无依赖 | 本题不应访问 crates.io |
| Python venv 复制失败 | xattr、truncate、symlink、Ext4 rename | 回跑 Python `fs`/`core` 模式 |
| `getent` 失败 | DHCP、`/etc/resolv.conf`、UDP auto-bind | 先查 `TOOLCHAIN_NETWORK_DIAG_*` |
| curl 连接 `10.0.2.2:27898` 超时 | 宿主中继和 7897 上游代理 | 中继未启动或上游代理端口不符 |
| curl HTTPS 成功但总验收失败 | `CURL_REMOTE_SIDE_EFFECT_OK`、27900 | 宿主未观察到 POST，不能只看下载 |
| 缺少 `online mask` | QEMU `-smp` 和平台上限 | 功能可能在更少 CPU 上运行，证据不匹配 |
| `qemu-img check` 失败 | 是否强杀 QEMU、磁盘是否并发打开 | 保留证据，使用全新覆盖层重跑 |

## 10. 维护规则

修改下列子系统后至少重跑对应测试：

| 修改区域 | 最小回归 |
|---|---|
| syscall 分发、信号 | `versions`、`build`、Cargo test、2025 timer 回归 |
| VFS/Ext4/stat/时间 | `build`、`cargo`、`python`、2025 Ext4、2026 ABI |
| fork/exec/wait/pipe/futex/SMP | RV4 `all`、RV8 `all`、LA12 `all` |
| VirtIO/DHCP/socket | `curl`、Python network、2025 network |
| LoongArch 平台代码 | 官方 Docker 重建加 LA12 `all`，不能只跑 RISC-V |
| 验证脚本 | 先分段，再至少一轮全新覆盖层 `all` |

任何新修复都应遵守：

1. 使用最小复现确认是内核问题，而不是测试脚本、镜像路径或宿主代理问题；
2. 实现通用 Linux/POSIX 语义，不检查应用名、不修改官方工具；
3. 同时验证返回码、结果内容和可观察副作用；
4. 保留失败和成功的串口日志、内核/镜像/脚本哈希及覆盖层检查；
5. 文档只声明实际跑过的架构、核数和工作负载，不用编译成功冒充动态通过。

## 11. 结论

六工具适配的实质不是新增六个内核“应用接口”，而是用真实构建和网络负载校验共同的 Linux 兼容面。本轮新发现并修复了一个“函数已写但 syscall 不可达”的信号分发缺口，以及一个自定义 Ext4 创建路径把时间戳留在 Epoch 0 的元数据缺口。结合此前 Python、Ext4、SMP 和网络适配，官方未修改工具已经在 RISC-V 4/8 核和 LoongArch 12 核完成同一套总验收。

后续若要继续提高比赛稳健性，优先事项是把 Ext4 extra timestamp 的纳秒部分贯通到 `Kstat/statx`，然后把 Ninja 测试收紧为首次 no-op 即不得补建；在完成并复测前，本文明确保留“秒级时间戳可能导致一次保守补建”的边界。

## 12. 现场开发与最终验收 SOP

本章给出真正到达比赛现场后应遵循的固定流程。它与前面的功能说明互补：前文回答“测什么、为什么这样实现”，本章回答“按什么顺序开发、何时可以宣布通过”。

### 12.1 总体闭环

```text
核对镜像、分支和内核
        ↓
只测六工具加载
        ↓
按 build/cargo/python/curl 分段测试
        ↓
提取一个最小失败用例
        ↓
确定 syscall/VFS/调度/网络责任层
        ↓
实现通用 Linux/POSIX 语义
        ↓
重跑失败分段和相关旧回归
        ↓
RV4 → RV8 → LA12 全新覆盖层总验收
        ↓
核对串口、哈希、CPU mask 和 qcow2
        ↓
检查暂存区并提交
```

任何一个计分点都必须同时满足：命令退出码为 0、输出结果正确、副作用正确、干净覆盖层可重复、覆盖层检查无错误。只满足其中一部分时，不应把该项记录为通过。

### 12.2 比赛开始：冻结基线

先确认输入文件和宿主能力，不要在镜像路径错误或旧内核上浪费时间：

```bash
cd ~/OS/oskernel2026test

git status --short
git branch --show-current
git rev-parse HEAD

ls -lh \
  testsuits-for-oskernel-final/image/sdcard-rv-pub.img \
  testsuits-for-oskernel-final/image/sdcard-la-pub.img

sha256sum \
  testsuits-for-oskernel-final/image/sdcard-rv-pub.img \
  testsuits-for-oskernel-final/image/sdcard-la-pub.img

qemu-system-riscv64 --version
qemu-img --version
docker image inspect zhouzhouyi/os-contest:20260510 >/dev/null
```

镜像哈希必须与第 2.1 节一致。开始修改前创建独立分支并记录恢复点：

```bash
git switch -c onsite-toolchain-competition
git rev-parse HEAD
git status --short
```

如果比赛已经提供固定分支，则留在该分支工作，不要为了套用上述名字改写官方要求的历史。

### 12.3 第一轮：只检查加载能力

构建当前源码，确认测试的不是旧内核：

```bash
make kernel-rv
stat kernel-rv
sha256sum kernel-rv
```

随后运行最浅层加载测试：

```bash
make verify-onsite-toolchain-versions
```

必须同时出现六个加载标记和正常驱动退出：

```text
MAKE_LOAD_OK
CMAKE_LOAD_OK
NINJA_LOAD_OK
CARGO_LOAD_OK
PYTHON_LOAD_OK
CURL_LOAD_OK

```

如果这里失败，先检查 ELF 动态加载、共享库、`mmap/mprotect`、`/proc/self/exe` 和缺失 syscall。加载测试未通过时，不应直接进入复杂的构建或联网测试。

### 12.4 第二轮：按功能分段定位

按以下顺序运行，每次只引入一类新的内核依赖：

```bash
make verify-onsite-toolchain-build
make verify-onsite-toolchain-cargo
make verify-onsite-toolchain-python
```

网络段需要先在终端 A 启动宿主中继：

```bash
cd ~/OS/oskernel2026test
make onsite-2025-proxy-relay
```

看到以下输出后保持该终端运行：

```text
proxy relay ready: 127.0.0.1:27898 -> 127.0.0.1:7897
```

然后在终端 B 运行：

```bash
cd ~/OS/oskernel2026test
make verify-onsite-toolchain-curl
```

各分段的最低通过标记如下：

| 分段 | 必须出现的功能标记 |
|---|---|
| `build` | `MAKE_BUILD_OK`、`CMAKE_MAKE_BUILD_OK`、`NINJA_BUILD_OK`、`CMAKE_NINJA_BUILD_OK` |
| `cargo` | `CARGO_BUILD_OK`、`CARGO_TEST_OK` |
| `python` | `PYTHON_TOOLCHAIN_OK` |
| `curl` | `CURL_HTTPS_OK`、`CURL_REMOTE_SIDE_EFFECT_OK` |

每段还必须出现 `TOOLCHAIN_DRIVER_DONE rc=0`。失败时不要立即反复运行总测试，应先打开本轮 evidence 目录：

```bash
rg -n 'FAILED|panic|Function not implemented|RC=|_OK|online mask' \
  artifacts/onsite-toolchain/<本轮目录>/serial.log
```

### 12.5 故障到内核子系统的映射

| 现场现象 | 首查方向 |
|---|---|
| 工具启动即 `Function not implemented` | syscall 号、分发、参数顺序和 errno |
| Make/CMake 子命令结束后卡住 | `fork/clone/execve/wait4`、SIGCHLD、pipe EOF |
| Ninja 报 `sigpending` | `rt_sigpending(136)` 和安全用户复制 |
| Ninja 每次都重建 | inode mtime、`stat/statx`、时间分辨率和缓存同步 |
| 编译完成却找不到产物 | Ext4 create/write/close/rename 和 dentry 缓存 |
| 并行构建随机卡死 | pipe、poll、futex、调度、锁顺序和任务回收 |
| Cargo 卡在网络 | 是否错误使用在线依赖；本题应保持 `--offline` |
| Cargo/rustc 大工程崩溃 | ELF、mmap、文件映射、资源限制和并发子进程 |
| Python venv/SQLite 失败 | truncate、xattr、symlink、rename、锁和文件长度 |
| Python 线程卡死 | futex、信号、TLS、clone 和任务唤醒 |
| DNS 失败 | DHCP、`resolv.conf`、UDP auto-bind 和真实来源地址 |
| TCP connect 卡住 | 非阻塞 connect、poll、`SO_ERROR` 和临时端口 |
| HTTPS 成功但 curl 总验收失败 | 宿主是否收到 27900 端口 POST 回执 |

网络故障必须按以下层次逐级定位，不能笼统归结为“网络不通”：

```text
DHCP → 地址/网关 → DNS → TCP connect → poll/SO_ERROR
     → HTTP CONNECT → TLS/CA → 内容哈希 → POST 副作用
```

### 12.6 单问题开发循环

每发现一个失败，都应执行一次完整的小闭环：

1. 保留原始串口日志和 QEMU 命令；
2. 把复杂失败缩减为一个命令或一个小型 C/Python 测试；
3. 确认是应用使用方式、镜像、宿主环境还是内核问题；
4. 找到准确的 syscall、VFS、调度或 socket 路径；
5. 实现通用 Linux/POSIX 语义；
6. 先重跑最小复现，再重跑对应分段；
7. 重跑可能受影响的旧回归；
8. 形成职责单一、可恢复的本地提交。

修复中禁止检查进程名、命令行、路径后缀或固定测试内容来伪造成功，也不能修改官方 Make、CMake、Ninja、Cargo、Python、curl 二进制和评分脚本。

### 12.7 修改后的最小回归矩阵

静态检查和 RISC-V 构建是所有修改的共同入口：

```bash
git diff --check
cargo check -p os --target riscv64gc-unknown-none-elf
make kernel-rv
```

然后根据修改范围选择最小回归：

| 修改区域 | 必须追加的回归 |
|---|---|
| syscall、信号 | `build`、`cargo`、`verify-onsite-2025-regressions` |
| VFS、Ext4、stat、时间 | `build`、`cargo`、`python`、2025 regressions、2026 ABI |
| fork/exec/wait/pipe/futex/SMP | RV4 `all`、RV8 `all`，随后 LA12 `all` |
| VirtIO、DHCP、socket | 2025 network、`curl`、Python network |
| LoongArch 平台代码 | 官方 Docker 重建和 LA12 `all` |

对应命令示例：

```bash
make verify-onsite-2025-regressions QEMU_SMP=4
make verify-onsite-2025-network QEMU_SMP=4
make verify-onsite-2026-abi QEMU_SMP=4
```

### 12.8 最终 RISC-V 验收

最终验收必须重新构建，并由验证器创建全新覆盖层。终端 A 保持代理中继运行，终端 B 执行：

```bash

git diff --check
make kernel-rv

make verify-onsite-toolchain-all TOOLCHAIN_ONSITE_SMP=4
make verify-onsite-toolchain-all TOOLCHAIN_ONSITE_SMP=8
```

RV4 必须同时出现：

```text
[smp] online mask 0xf
TOOLCHAIN_COMBINED_OK
CURL_HTTPS_OK
CURL_REMOTE_SIDE_EFFECT_OK
TOOLCHAIN_ONSITE_ALL_OK
TOOLCHAIN_DRIVER_DONE rc=0
```

RV8 必须至少再次出现完整功能标记，并包含：

```text
[smp] online mask 0xff
TOOLCHAIN_ONSITE_ALL_OK
TOOLCHAIN_DRIVER_DONE rc=0
```

只看到完整 CPU mask 不能证明工具功能通过；只看到工具标记但缺少预期 CPU mask，也不能作为目标核数的多核证据。
