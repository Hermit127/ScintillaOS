## 2. 分支迁移和提交入口

`finalsubmission` 原先只自动执行 CAgent。本轮将 `main` 当前提交
`df511f76` 的内核能力合并进来，保留决赛提交分支的自动评测入口，并对
`user/src/bin/initproc.rs` 做最小扩展：

1. 挂载官方测试盘 `vda` 到 `/mnt`；
2. `chroot` 到测试盘并进入 `/glibc`；
3. 原样执行官方 `./cagent_testcode.sh`；
4. 真实执行 `rustc --version`、`cargo --version`；
5. 真实执行 `cargo new --vcs none /tmp/minibuild` 和 `cargo build`；
6. 运行新生成的二进制，并只在输出等于 `Hello, world!` 时打印
   `BUILDSTORM_MINIBUILD ok`；
7. Q2.1 完成后调用内核关机系统调用。

每个测试由独立 child 执行，父进程用 `waitpid` 等待真实退出状态。失败路径会打印
`fail` 或明确错误信息，不会无条件打印成功标记。

## 3. RISC-V 多核陷阱返回竞态

### 3.1 表现

初始八核 RISC-V 长测保留 VirtIO-Net 后，CAgent 偶发只输出 8 个结果，两个 CPU
长期停在 `user_restore`。其余 CPU 已进入 idle，说明问题不是普通用户进程仍在计算，
而是部分 hart 无法从内核正确返回用户态。

### 3.2 GDB 证据

检查两个异常 hart 的 trap frame 后发现：

```text
saved sepc = user_restore + 0x2c
saved sstatus.SPP = Supervisor
```

用户 trap frame 本应保存用户 PC 和用户权限状态，却被一次发生在
`user_restore` 中间窗口的 supervisor timer interrupt 覆盖。RISC-V 返回路径先把
用户 trap frame 地址写入 `sscratch`，随后逐个恢复寄存器并执行 `sret`。若本地中断
在这段窗口内仍然开启，timer interrupt 会看到非零 `sscratch`，错误选择 `uservec`
入口，并把当前内核 `sepc`、栈和状态写进用户 frame。之后 `sret` 又返回
`user_restore`，形成永久循环。

### 3.3 通用修复

修改位置：`os/src/task/task.rs::task_entry()`。

进入 `run_user_task()` 前关闭当前 hart 的本地中断，使“发布用户 trap frame到执行
最终返回指令”成为不可重入区间。用户中断状态仍由 trap frame 中的状态寄存器在
`sret`/对应架构返回指令时恢复，因此没有永久关闭用户态中断，也没有禁用 VirtIO
设备。该做法修复的是内核陷阱返回边界，不依赖 CAgent 的进程名、请求数量或超时。

修复后，RISC-V 在相同八核和网卡配置下稳定输出 10 个 CAgent 结果，并继续完成
Rust 最小构建。

## 4. LoongArch VirtIO-Net 增量适配

### 4.1 原有缺口

LoongArch 的 QEMU `virt` 平台使用 PCI VirtIO 设备。合并前存在以下不一致：

1. VirtIO 块设备已经使用 `PciRoot` 和 `PciTransport`；
2. VirtIO 网卡仍扫描 RISC-V 风格的 MMIO 地址；
3. `net_init()`、`net_poll()`、`with_net_iface()` 和网络阻塞唤醒在 LoongArch 上是
   空实现；
4. Makefile 没有为 LoongArch 添加 `virtio-net-pci`。

因此“QEMU 命令带网卡”不等于“内核使用网卡”。本轮没有去掉设备，而是补全传输层。

### 4.2 PCI 枚举与 BAR

修改位置：`os/src/drivers/net/virtio_net.rs`。

RISC-V 和 AArch64 保持原来的 `MmioTransport`，LoongArch 使用
`PciTransport`。LoongArch 初始化流程为：

1. 从 ECAM 基址 `0x2000_0000` 枚举 PCI bus 0；
2. 用 `virtio_device_type()` 选择 `DeviceType::Network`；
3. 为尚未分配地址的 memory BAR 分配空间；
4. 块设备 BAR 使用 `0x4000_0000` 区域，网卡使用独立的 `0x5000_0000` 区域，
   避免两个驱动重复映射；
5. 启用 PCI `MEMORY_SPACE` 和 `BUS_MASTER`；
6. 构造 `PciTransport` 和现有 `VirtIONet`，继续复用同一套 smoltcp adapter。

启动日志证明网卡是实际识别而非软件假定存在：

```text
[net] VirtIO PCI network device DeviceFunction { bus: 0, device: 2, function: 0 } found
[net] VirtIONetAdapter initialized successfully, MAC=[52, 54, 00, 12, 34, 56]
[net] VirtIO-Net initialized, MAC=[52, 54, 00, 12, 34, 56]
```

### 4.3 网络状态机复用

修改位置：`os/src/net/mod.rs`。

LoongArch 现在与 RISC-V/AArch64 一样执行：

- `NET_IFACE` 和 `NET_INITED` 初始化；
- smoltcp interface/socket set 轮询；
- TCP connect、send、recv 和 UDP 路径访问；
- 网络阻塞任务 readiness 检查与唤醒；
- 软件 loopback 和真实 VirtIO 硬件队列协同。

CAgent 的 LLM server 监听 `127.0.0.1:8080`。LoongArch 日志中出现真实 HTTP POST，
网络测试也被官方 judge 判为通过，说明新增 PCI 设备没有破坏既有 loopback 行为。

### 4.4 QEMU 配置

修改位置：`Makefile`。

LoongArch 增加：

```make
-netdev user,id=net0,... -device virtio-net-pci,netdev=net0
```

RISC-V/AArch64 原有 `virtio-net-device` MMIO 配置保持不变。

## 5. lwext4 构建稳定性

修改位置：`lwext4_rust/build.rs`。

旧逻辑根据 Git checkout 后不稳定的 mtime 判断是否重编 `lwext4`，容易在分支切换或
全新 clone 后无必要地重建静态库，并可能使用宿主环境中不一致的 C 工具链。新逻辑：

1. 工具链文件按内容比较，仅在内容不同时复制；
2. 默认使用仓库中已经跟踪的架构静态库；
3. 静态库缺失时才自动重建；
4. 需要主动重建时使用 `LWEXT4_FORCE_REBUILD=1`；
5. 通过 `rerun-if-env-changed` 让 Cargo 正确感知该开关。

这项修改只改变构建可重复性，不改变 ext4 运行时语义。

## 10. 2026-08-05 官网回归与修复

### 10.1 官网失败现象

提交 `ecc1a5fe` 的官网结果为 CAgent RISC-V 165.05 分、LoongArch 141 分，BuildStorm
两架构均为 0 分。串口日志显示：

- RISC-V 的 `fs-directory` 在 37055 ms 后失败；
- LoongArch 的 `network` 和 `fs-directory` 分别在 41964 ms、40782 ms 后失败；
- RISC-V 实际完成了 toolchain 和 minibuild；当时仅依据公开单文件 judge，曾把
  `buildstorm-glibc` 初步判断为错误组名，这个判断后来被 2026-08-06 官网日志推翻；
- LoongArch 只输出 `BUILDSTORM_TOOLCHAIN ok`，没有到达 minibuild 和组结束标记。

这说明问题不是命令本身缺失，而是十个并发 CAgent 客户端使内核网络对象分配和锁
竞争被放大，随后又影响到 Rust 最小构建；同时 BuildStorm 还存在独立的输出归组错误。

### 10.2 本地 TCP 对象生命周期修复

CAgent 的服务端和客户端都通过 `127.0.0.1` 通信。旧实现接受一条本地连接时仍调用
`add_to_socket_set` 创建 smoltcp TCP socket，为每条 accepted 连接分配两个 64 KiB
缓冲区；实际读写却全部进入 `LocalTcpConn` 软件回环队列，这个 smoltcp 对象从未参与
数据传输。十个请求并发时，这些无效的 128 KiB 对象造成明显的堆分配、清零和网络锁
压力，并在关闭时再次进入全局 socket set。

修复后，`SocketFileState.handle` 改为 `Option<SocketHandle>`。普通 TCP/UDP 和真实 VirtIO
网卡连接保存 `Some(handle)`；仅由本地监听器接受的回环连接使用 `None`，并通过
`SocketFile::new_local_tcp` 创建。`read`、`write`、`poll`、`close`、`sendto`、
`recvfrom`、`sendmsg`、`recvmsg`、socket option、`shutdown`、`getpeername` 和
`getsockname` 都显式区分两条路径。无 handle 的对象不会访问或释放 smoltcp，真实网卡
路径则必须持有有效 handle，否则返回 `ENOTCONN`。虚拟网卡及外部网络实现均被保留。

`bind` 原先会提前把 TCP 端口登记到本地监听表，使客户端有机会在服务端执行
`listen` 前连接。现在端口只在 `sys_listen` 成功后登记，状态转换与 Linux 的
`socket -> bind -> listen -> accept` 语义一致。

### 10.3 当时的输出协议判断

当时 initproc 中 BuildStorm 的开始和结束标记曾改为公开源码原始脚本使用的：

```text

#### OS COMP TEST GROUP END buildstorm ####
```

`BUILDSTORM_TOOLCHAIN ok` 和 `BUILDSTORM_MINIBUILD ok` 保持不变，二者正是官方 judge
分别结算 8 分和 12 分的记录。CAgent 仍先运行，随后执行真实 `cargo new`、

后续官网输出证明，平台会先按带 libc 后缀的组名抽取日志，再调用单文件 judge；因此

## 11. 2026-08-06 官网输出 9 回归与最终修复

### 11.1 官网现象与评分归组根因

官网结果中，RISC-V 的 CAgent 通过 9/10，`fs-directory` 在 35585 ms 后失败；
LoongArch 的 CAgent 通过 9/10，`network` 在 37577 ms 后失败。两架构串口都真实输出
了 `BUILDSTORM_TOOLCHAIN ok`、`BUILDSTORM_MINIBUILD ok` 和组结束标记，但 BuildStorm
评分仍为 0。

协议问题不能归结为单独一个组名。上一份官网输出 8 使用 `buildstorm-glibc`，RISC-V
也完整输出两条 `BUILDSTORM_*` 成功记录，评分仍为 0；输出 9 改成 `buildstorm` 后仍为
0。公开仓库本身存在版本错位：生成 glibc 测试盘的 Makefile 会给组名追加 `-glibc`，
README 要求 `TOOLCHAIN_RESULT/MINIBUILD_RESULT`，当前脚本和 judge 则改为
`BUILDSTORM_TOOLCHAIN/BUILDSTORM_MINIBUILD`。官网 CAgent 又使用 `success/fail`，而公开
脚本使用 `pass/reject`，进一步证明平台包装器与仓库当前版本并不完全一致。

因此最终策略是同时兼容日志分组和两代结果协议，而不是猜测官网只使用其中一版。

最终输出同时满足当前公开 judge 和旧版平台协议：

```text
#### OS COMP TEST GROUP START buildstorm-glibc ####
BUILDSTORM_TOOLCHAIN ok
TOOLCHAIN_RESULT status=OK
BUILDSTORM_MINIBUILD ok
MINIBUILD_RESULT status=OK
#### OS COMP TEST GROUP END buildstorm-glibc ####
```

两套结果标记都只在对应命令真实成功后输出；失败分支输出 `fail/FAIL`，没有伪造构建
结果。测试仍执行镜像内真实的 `rustc --version`、`cargo --version`、`cargo new`、
`cargo build` 和生成程序。

### 11.2 调度上下文与 CPU 亲和性

`schedule` 过去在保存任务上下文和移交 per-CPU `current` 所有权时允许本地定时器或 IPI
重入，可能让中断观察到尚未保存完毕的上下文。现在上下文切换前保存中断状态并关闭
本地中断，恢复到原任务后再按原状态开启，使上下文保存、页表切换和 current 所有权
移交成为同一 CPU 上不可重入的区间。

旧 `sys_fork` 会把 PID 1 的直接子进程固定在 CPU0，而 fork/clone 创建的后代又没有
继承父进程亲和性，行为既不符合 Linux，也会使自动测试入口形成意外瓶颈。现在 fork
与共享地址空间 clone 都在发布子任务前继承父任务 CPU mask，并移除 PID 1 的特殊固定；
默认 mask 覆盖所有在线 CPU，因此 CAgent 的 shell、十个 agent 和辅助进程能够正常
分布到各核。

### 11.3 LoongArch 12 核与调度时间片

官网 QEMU 使用 `-smp 12`，但旧内核把 `MAX_CPUS` 和 LoongArch `PLATFORM_CPUS` 都限制为
8，hart 8 至 11 被永久停放，官网日志中的在线掩码只有 `0xff`。现在调度器数组容量
扩展为 12，RISC-V 仍使用 8 核，LoongArch 使用完整 12 核。实测 hart 0 至 11 都建立
独立 per-CPU 区、实际取得用户任务，在线掩码为 `0xfff`。

LoongArch HAL 的定时器频率为 1 kHz，旧调度器把每个 1 ms tick 都直接当作用户时间片
结束；12 核负载下会产生每秒约 12000 次上下文切换。修复后仍以 1 ms 处理睡眠截止、
网络轮询和 interval timer，只在累计 10 个 tick 后进行一次用户任务抢占。这样保留
时间精度，同时使用与 RISC-V 100 Hz 定时器一致的 10 ms 调度量级。

### 11.4 睡眠防丢唤醒与回环 TCP

`nanosleep` 从反复 yield 的忙等改为进入调度器睡眠队列，截止时由 hart 0 的 1 ms
timekeeper 唤醒。为了符合 Linux 的可中断睡眠语义，任务先原子登记阻塞，再复查截止
时间、killed 状态和未屏蔽信号；条件已经变化时取消阻塞。信号在检查前、登记后或上下文
切换期间到达都不会丢失，BusyBox `timeout` 不再因竞态一直等到原截止时间。

本地 TCP 仍使用有界的双向 `VecDeque` 和原有阻塞/唤醒协议，但发送与接收从逐字节
push/pop 改为按环形缓冲区两段批量复制。修改不改变 256 KiB 上限、非阻塞返回值、peek
或关闭语义，只缩短十路 HTTP 通信持有 `Net.local_tcp_connections` 锁的时间。

## 12. 2026-08-10 启用完整 BuildStorm 最终入口

此前 `finalsubmission` 的自动入口只执行 CAgent 和一段内嵌的 BuildStorm 2.1 检查，
随后立即关机。该入口能够验证工具链与最小工程，却不会进入复杂软件构建，因此无论
内核已经具备多少 2.2 兼容性，官网都不可能看到 `BUILDSTORM_COMPILE` 结果。

本轮将入口调整为先执行 `cagent_testcode.sh`，再直接执行测试盘中的官方
`buildstorm_testcode.sh`，脚本返回后才关机。官方脚本内部顺序为工具链检查、最小工程
构建、`tg-xtask` 准备和 `cargo xtask arceos build`；因此 CAgent 与 2.1 仍优先结算，
完整 2.2 位于最后。入口不复制评分逻辑，也不自行生成成功标记，所有结果均由镜像中的
真实 `rustc`、`cargo`、链接器和最终产物检查决定。

合并后的 RISC-V release 内核已完成构建验证。此前在 `main` 上进行的干净 BuildStorm
长测中，2.1 的 toolchain 与 minibuild 均通过，随后 `tg-xtask` 冷构建推进至 60/446；
为了及时迁移代码而人工中止，故这一数据只能证明 2.2 已经进入真实编译阶段，不能声称
完整编译通过。LoongArch 本机缺少对应交叉 C 编译器，完整双架构 2.2 仍需在官方环境
继续验证。
