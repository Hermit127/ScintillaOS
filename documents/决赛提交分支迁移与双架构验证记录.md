## 2. 分支迁移和提交入口

`finalsubmission` 原先只自动执行 CAgent。本轮将 `main` 当前提交
`df511f76` 的内核能力合并进来，保留决赛提交分支的自动评测入口，并对
`user/src/bin/initproc.rs` 做最小扩展：

1. 挂载官方测试盘 `vda` 到 `/mnt`；
2. `chroot` 到测试盘并进入 `/glibc`；
3. 原样执行官方 `./cagent_testcode.sh`；
4. 真实执行 `rustc --version`、`cargo --version`；
5. 真实执行 `cargo new --vcs none /tmp/minibuild` 和 `cargo build`；
6. 运行新生成的二进制，并只在输出等于 `Hello, world!` 时打印
   `BUILDSTORM_MINIBUILD ok`；
7. Q2.1 完成后调用内核关机系统调用。

每个测试由独立 child 执行，父进程用 `waitpid` 等待真实退出状态。失败路径会打印
`fail` 或明确错误信息，不会无条件打印成功标记。

## 3. RISC-V 多核陷阱返回竞态

### 3.1 表现

初始八核 RISC-V 长测保留 VirtIO-Net 后，CAgent 偶发只输出 8 个结果，两个 CPU
长期停在 `user_restore`。其余 CPU 已进入 idle，说明问题不是普通用户进程仍在计算，
而是部分 hart 无法从内核正确返回用户态。

### 3.2 GDB 证据

检查两个异常 hart 的 trap frame 后发现：

```text
saved sepc = user_restore + 0x2c
saved sstatus.SPP = Supervisor
```

用户 trap frame 本应保存用户 PC 和用户权限状态，却被一次发生在
`user_restore` 中间窗口的 supervisor timer interrupt 覆盖。RISC-V 返回路径先把
用户 trap frame 地址写入 `sscratch`，随后逐个恢复寄存器并执行 `sret`。若本地中断
在这段窗口内仍然开启，timer interrupt 会看到非零 `sscratch`，错误选择 `uservec`
入口，并把当前内核 `sepc`、栈和状态写进用户 frame。之后 `sret` 又返回
`user_restore`，形成永久循环。

### 3.3 通用修复

修改位置：`os/src/task/task.rs::task_entry()`。

进入 `run_user_task()` 前关闭当前 hart 的本地中断，使“发布用户 trap frame到执行
最终返回指令”成为不可重入区间。用户中断状态仍由 trap frame 中的状态寄存器在
`sret`/对应架构返回指令时恢复，因此没有永久关闭用户态中断，也没有禁用 VirtIO
设备。该做法修复的是内核陷阱返回边界，不依赖 CAgent 的进程名、请求数量或超时。

修复后，RISC-V 在相同八核和网卡配置下稳定输出 10 个 CAgent 结果，并继续完成
Rust 最小构建。

## 4. LoongArch VirtIO-Net 增量适配

### 4.1 原有缺口

LoongArch 的 QEMU `virt` 平台使用 PCI VirtIO 设备。合并前存在以下不一致：

1. VirtIO 块设备已经使用 `PciRoot` 和 `PciTransport`；
2. VirtIO 网卡仍扫描 RISC-V 风格的 MMIO 地址；
3. `net_init()`、`net_poll()`、`with_net_iface()` 和网络阻塞唤醒在 LoongArch 上是
   空实现；
4. Makefile 没有为 LoongArch 添加 `virtio-net-pci`。

因此“QEMU 命令带网卡”不等于“内核使用网卡”。本轮没有去掉设备，而是补全传输层。

### 4.2 PCI 枚举与 BAR

修改位置：`os/src/drivers/net/virtio_net.rs`。

RISC-V 和 AArch64 保持原来的 `MmioTransport`，LoongArch 使用
`PciTransport`。LoongArch 初始化流程为：

1. 从 ECAM 基址 `0x2000_0000` 枚举 PCI bus 0；
2. 用 `virtio_device_type()` 选择 `DeviceType::Network`；
3. 为尚未分配地址的 memory BAR 分配空间；
4. 块设备 BAR 使用 `0x4000_0000` 区域，网卡使用独立的 `0x5000_0000` 区域，
   避免两个驱动重复映射；
5. 启用 PCI `MEMORY_SPACE` 和 `BUS_MASTER`；
6. 构造 `PciTransport` 和现有 `VirtIONet`，继续复用同一套 smoltcp adapter。

启动日志证明网卡是实际识别而非软件假定存在：

```text
[net] VirtIO PCI network device DeviceFunction { bus: 0, device: 2, function: 0 } found
[net] VirtIONetAdapter initialized successfully, MAC=[52, 54, 00, 12, 34, 56]
[net] VirtIO-Net initialized, MAC=[52, 54, 00, 12, 34, 56]
```

### 4.3 网络状态机复用

修改位置：`os/src/net/mod.rs`。

LoongArch 现在与 RISC-V/AArch64 一样执行：

- `NET_IFACE` 和 `NET_INITED` 初始化；
- smoltcp interface/socket set 轮询；
- TCP connect、send、recv 和 UDP 路径访问；
- 网络阻塞任务 readiness 检查与唤醒；
- 软件 loopback 和真实 VirtIO 硬件队列协同。

CAgent 的 LLM server 监听 `127.0.0.1:8080`。LoongArch 日志中出现真实 HTTP POST，
网络测试也被官方 judge 判为通过，说明新增 PCI 设备没有破坏既有 loopback 行为。

### 4.4 QEMU 配置

修改位置：`Makefile`。

LoongArch 增加：

```make
-netdev user,id=net0,... -device virtio-net-pci,netdev=net0
```

RISC-V/AArch64 原有 `virtio-net-device` MMIO 配置保持不变。

## 5. lwext4 构建稳定性

修改位置：`lwext4_rust/build.rs`。

旧逻辑根据 Git checkout 后不稳定的 mtime 判断是否重编 `lwext4`，容易在分支切换或
全新 clone 后无必要地重建静态库，并可能使用宿主环境中不一致的 C 工具链。新逻辑：

1. 工具链文件按内容比较，仅在内容不同时复制；
2. 默认使用仓库中已经跟踪的架构静态库；
3. 静态库缺失时才自动重建；
4. 需要主动重建时使用 `LWEXT4_FORCE_REBUILD=1`；
5. 通过 `rerun-if-env-changed` 让 Cargo 正确感知该开关。

这项修改只改变构建可重复性，不改变 ext4 运行时语义。

## 8. 可复现配置与完整性说明

测试使用官方原始镜像的 QEMU `-snapshot` 模式，所有写入都位于临时快照，不修改
下载的测试盘。两种架构都使用 `-smp 8`、`-m 2G`，并显式连接对应 VirtIO 网卡。

复现时应先构建两个 release 内核：

```sh
make kernel-rv
make kernel-la
```

RISC-V 使用 `target/riscv64gc-unknown-none-elf/release/os.bin`，LoongArch 使用
`target/loongarch64-unknown-none/release/os`。官方盘分别作为唯一的 `vda` 连接，
initproc 会自动完成挂载、CAgent、Q2.1 和关机。

本轮没有执行以下行为：

- 没有删除或屏蔽 QEMU 虚拟网卡；
- 没有修改 CAgent/BuildStorm 官方脚本和用户态二进制；
- 没有改写系统时钟或 `/proc/uptime`；
- 没有预置 `minibuild` 产物；
- 没有在系统调用中按测试名、路径或输出内容返回固定成功值。
