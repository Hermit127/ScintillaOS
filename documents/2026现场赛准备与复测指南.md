# 2026 现场赛准备、复测与性能验证指南

本文记录从 2025 现场赛兼容分支继续准备 2026 现场赛的依据、当前实现、已验证范围、正式镜像复测流程和性能优化纪律。它既是比赛前检查表，也是发生回归时的恢复手册。

## 1. 先说结论：2026 题目已经公开，不再只是猜测

本项目旁的官方测试仓库 `../testsuits-for-oskernel` 已给出 2026 决赛题目、脚本和公开 judge。决赛有两题，两题各占最终成绩的 50%，并要求初赛测例仍能通过：

1. **CAgent（glibc，200 分）**：在客体中运行本地 LLM 服务和十个并发 agent 任务，检查命令执行、日期、CPU/内核信息、TCP 状态及文件系统操作。正确性之外还有耗时奖励。
2. **BuildStorm（glibc，200 分）**：在 Debian 大镜像中运行 Rust 工具链，先完成最小 Cargo 项目，再以多核从源码构建 `arceos-helloworld`。其中工具链 8 分、最小构建 12 分、正式构建成功 40 分、相对 Linux 基线的耗时 120 分，另有 20 分设计与优化文档。

官方 RISC-V 配置是 `-smp 8 -m 8G`；公开 judge 期望 RISC-V 看到 8 核。LoongArch 公开 judge 期望 12 核。两平台都必须使用 glibc 用户态，不能以 Alpine/musl 的通过结果替代。

因此，2025 年“让 Git、Vim、GCC、Rustc 在 Alpine 上真实运行”的题型，已经演化成 2026 年“让并发 agent 和大型 Rust 构建在 Debian/glibc、多核和重 I/O 下长期稳定运行”。准备重点应从单个程序的缺失 syscall，转向组合语义、并发正确性、资源回收和性能。

官方原始说明和脚本以以下本地文件为准：

- `../testsuits-for-oskernel/README.md`
- `../testsuits-for-oskernel/scripts/cagent_testcode.sh`
- `../testsuits-for-oskernel/scripts/buildstorm_testcode.sh`
- `../testsuits-for-oskernel/judge/judge_cagent-glibc.py`
- `../testsuits-for-oskernel/judge/judge_buildstorm-glibc.py`

## 2. 由 2025 题目可以推导出的隐藏风险

2025 的经验仍然有效：版本命令能运行，不代表真实功能可用。Git 的覆盖重命名、Vim 的 timer/TTY、GCC 的文件长度一致性、HTTPS 的 DNS/TCP 都是在深入路径才暴露问题。2026 也应按同样原则准备。

| 公开工作负载 | 很可能触发的内核路径 | 只做表面测试的风险 |
|---|---|---|
| 十个并发 CAgent 子任务 | `clone/exec/wait4`、pipe、信号、定时器、loopback TCP、procfs、目录遍历 | 单进程命令成功，但并发时丢唤醒、泄漏或超时 |
| `rustc`/`cargo` 动态加载 | glibc TLS、robust futex、`rseq` 兼容返回、文件映射、`mprotect`、`readlink` | `--version` 成功，但链接或多线程代码生成失败 |
| Cargo 依赖扫描 | 大量 `openat/statx/getdents64/readlinkat`、负查找、页缓存 | 正确但目录/元数据路径过慢 |
| Rust 并行代码生成 | 8/12 核调度、futex、pipe、eventfd/epoll、timerfd | 低负载通过，长时间高并发死锁或饥饿 |
| 链接与产物写回 | 大文件 mmap、truncate、稀疏写、rename、fsync、Ext4 锁序 | 末尾链接失败、文件长度陈旧或缓存不一致 |
| 4 小时级构建 | fd/页表/任务/缓存回收、超时唤醒、整数溢出 | 短测通过，后期 OOM、fd 耗尽或计时错误 |

比赛前还应防备脚本未显式列出的同类接口，例如 `signalfd`、更完整的 `epoll_pwait` 掩码语义、`faccessat2`、`openat2`、`close_range`、`statx` 字段、`madvise`、`prlimit64` 和 `/proc/self/fd`。正确策略不是提前伪造所有 syscall，而是建立 `ENOSYS` 诊断，在真实工作负载首次命中后做最小复现和 Linux 语义修复。

## 4. 已完成的 2026 兼容准备

### 4.1 timerfd 与 epoll 组合语义

新增 `os/src/fs/timerfd.rs`，并在 `os/src/syscall/fs.rs`、`os/src/syscall/mod.rs` 和 `os/src/task/mod.rs` 接入：

- `timerfd_create`、`timerfd_settime`、`timerfd_gettime`；
- `CLOCK_REALTIME`、`CLOCK_MONOTONIC`、`CLOCK_BOOTTIME`；
- 相对/绝对到期、周期累计、撤销、非阻塞 `EAGAIN`；
- 8 字节到期次数读取；
- poll/epoll 就绪代际和任务唤醒；
- 弱引用全局表，fd 最后关闭后不永久持有对象。

timerfd 与已有 POSIX timer 共用内核定时器 deadline 提示。设置或到期会唤醒 poll 等待者；读出累计次数后清除就绪状态。实现针对的是 Linux fd 语义，不按程序名特判。

### 4.2 预防 glibc/大型构建的 ABI 回归

新增 `tests/onsite2026/abi_regression.c` 和 `make verify-onsite-2026-abi`。回归覆盖：

- `/proc/uptime`、`/proc/cpuinfo`、`/proc/meminfo`、`/proc/mounts`、`/proc/self/exe`；
- eventfd 非阻塞读取及 epoll 通知；
- timerfd 周期到期、epoll、读取和撤销；
- 跨页 `MAP_SHARED` 写回、`MAP_PRIVATE` 隔离和 `mremap` 扩容；
- glibc robust pthread：线程持锁退出后返回 `EOWNERDEAD`，再 consistent/unlock；
- 64 轮 eventfd/timerfd/epoll 和匿名映射创建销毁，比较 `MemAvailable`，防止明显资源泄漏。

四核新覆盖层实测已出现全部标记：

```text
ABI2026_PROCFS_OK
ABI2026_EVENTFD_EPOLL_OK
ABI2026_TIMERFD_OK
ABI2026_FILE_MAPPING_OK
ABI2026_GLIBC_THREAD_OK
ABI2026_RESOURCE_RECLAIM_OK
ABI2026_REGRESSION_OK
ABI2026_TEST_RC=0
```

这证明小型组合回归通过，不等价于完整 BuildStorm 已通过。

### 4.3 八核和低扰动诊断

`scripts/validate_smp4.py` 已泛化为 `--smp 1..8`，成功条件按核数计算 online/observed mask；启动前还会抽取根盘 `/bin/user_shell` 的 ELF 机器号，避免把 LoongArch 根盘误用于 RISC-V。此前 `fs-img.img` 中恰好是 LoongArch 用户程序，这个保护成功阻止了一次错误归因。

八核 release 定向回归已在 `disk.img` 上通过，证据曾保存于：

```text
artifacts/smp8-preflight-release-v3/
online mask = 0xff
observed = 0xff
```

低扰动诊断内核目标 `make kernel-rv-final-diag` 启用：

```text
lockdep
lock-stats
scheduler-stall-diagnostics
buildstorm-mm-diagnostics
unknown-syscall-diagnostics
```

该诊断配置的八核定向回归也通过。验证器现在会在每轮结束后保存两个 overlay 的 `qemu-img check` 输出。不要用输出量巨大的全量 SMP trace 跑性能测例；串口打印会改变时序和得分。

### 4.4 正式 2026 运行器

新增 `scripts/run_final_2026.py`：

1. 检查 kernel、根盘、官方测试盘和 QEMU；
2. 校验根盘 ELF 架构；
3. 为官方测试盘和项目根盘分别建立全新 qcow2 overlay；
4. 记录 Git 状态、输入 SHA-256、QEMU 版本、拓扑和完整命令；
5. 通过串口挂载测试盘，把驱动放入测试盘 `/tmp`，再 chroot 到官方 glibc 环境；
6. 执行 CAgent、2.1 小构建、BuildStorm 或全部流程；
7. 严格检查十个 CAgent `pass`、工具链/小构建标记、正式构建成功标记和在线 CPU mask；
8. 保存未剪辑串口日志、公开 judge 输出及两个 overlay 的 `qemu-img check`。

LoongArch 可通过 `scripts/run_final_2026_docker.sh` 使用官方容器 `zhouzhouyi/os-contest:20260510` 内的 QEMU 10.0.2。容器以宿主 UID/GID 和临时 HOME 运行，避免生成 root 所有权文件。

## 6. 获取并校验官方大镜像

官方仓库 README 当前给出的下载入口是百度网盘，提取码 `kyva`。历史压缩名可能是 `sdcard-rv.img.xz`、`sdcard-la.img.xz`，运行器默认寻找解压后的：

```text
testsuits-for-oskernel-final/image/sdcard-rv-pub.img
testsuits-for-oskernel-final/image/sdcard-la-pub.img
```

下载后不要直接写 raw 镜像。先记录来源和哈希：

```bash
mkdir -p testsuits-for-oskernel-final/image
sha256sum testsuits-for-oskernel-final/image/sdcard-*-pub.img
qemu-img info testsuits-for-oskernel-final/image/sdcard-rv-pub.img
e2fsck -fn testsuits-for-oskernel-final/image/sdcard-rv-pub.img
qemu-img info testsuits-for-oskernel-final/image/sdcard-la-pub.img
e2fsck -fn testsuits-for-oskernel-final/image/sdcard-la-pub.img
```

官方基盘是 raw Ext4，`qemu-img check` 对 raw 格式会报告“不支持 checks”；这不是镜像损坏。只读检查基盘用 `e2fsck -fn`，运行后生成的 qcow2 overlay 才用 `qemu-img check`。

如果拿到的是 `.xz`，保留压缩原件，只解压出新的 raw 文件。约 14 GiB 的镜像和 overlay 需要充足磁盘空间。

## 7. 正式复测顺序

### 7.1 静态检查和构建

```bash
git status --short
git diff --check
python3 -m py_compile scripts/run_final_2026.py scripts/validate_smp4.py
sh -n scripts/run_final_2026_docker.sh
make kernel-rv
make disk.img
```

LoongArch 使用官方 Docker 工具链构建；宿主当前没有 LoongArch QEMU/GCC，不要把宿主命令失败误判为源码失败。

### 7.2 先跑短回归

```bash
make verify-onsite-2026-abi QEMU_SMP=4

python3 scripts/validate_smp4.py \
  --kernel kernel-rv \
  --root-disk disk.img \
  --test-disk test_disk.img \
  --suite directed \
  --rounds 1 \
  --smp 8 \
  --memory 1G \
  --output-dir artifacts/smp8-preflight-$(date +%Y%m%dT%H%M%S)
```

短回归失败时不要直接进入六小时 BuildStorm。

### 7.3 RISC-V 官方镜像

先分题运行，最后运行 `all`：

```bash
make run-final-2026-rv FINAL_2026_MODE=cagent
make run-final-2026-rv FINAL_2026_MODE=q21
make run-final-2026-rv FINAL_2026_MODE=buildstorm
make run-final-2026-rv FINAL_2026_MODE=all
```

每轮应产生 `artifacts/final2026/<UTC时间>-riscv64-<模式>/`，至少包含：

```text
metadata.json
qemu-command.txt
serial.log
cagent-judge.json 或 buildstorm-judge.json
test-overlay-check.txt
root-overlay-check.txt
```

通过必须同时满足：驱动 `rc=0`、公开脚本标记齐全、online mask 为 `0xff`、judge 得分符合预期、overlay 无错误。

### 7.4 LoongArch 官方镜像

先在不依赖官方大镜像的情况下验证 12 核基础动态环境：

```bash
make verify-loongarch12-boot-docker
```

验证器必须看到 `online mask 0xfff`、进入 Rust user shell、运行 `cpuinfotest` 成功，并保存串口、输入哈希、QEMU 命令及 overlay 检查。随后使用官方大镜像：

```bash
make run-final-2026-la-docker FINAL_2026_MODE=cagent
make run-final-2026-la-docker FINAL_2026_MODE=q21
make run-final-2026-la-docker FINAL_2026_MODE=buildstorm
make run-final-2026-la-docker FINAL_2026_MODE=all
```

通过时应看到 12 核在线掩码 `0xfff`。若官方容器中的 QEMU 设备拓扑与项目 LoongArch VirtIO 实现不一致，应先对照原有 `run-la-*` Make 目标修正运行器，不能为了出现标记而改官方脚本。

正式提交前仍需跑：

## 8. 故障定位顺序

### 8.1 CAgent

1. 先找 `reject` 的精确 case；
2. 保留该任务输出文件，单独执行同一 prompt；
3. 区分 agent/本地 LLM 服务失败、命令失败、验证命令失败和 timeout；
4. network case 优先检查 `/proc/net/tcp` 或所调用工具需要的 netlink/procfs；
5. 十个任务并发失败但单个通过，检查 wait/信号、loopback socket、fd 和调度公平性。

### 8.2 BuildStorm

按阶段缩小范围：

1. `rustc --version`/`cargo --version`：动态加载、TLS、procfs、基础 mmap；
2. `cargo new`：目录、rename、权限和时间戳；
3. minibuild 编译：线程/futex、pipe、文件映射、链接；
4. `tg-xtask`：依赖扫描和 proc macro；
5. 正式构建：长时间并发、页缓存、Ext4 写回和资源回收；
6. 最终链接：大映射、truncate、随机访问、产物长度和同步。

诊断构建只记录失败和低频统计：

```bash
make kernel-rv-final-diag
```

重点搜索：

```bash
rg -n 'unknown syscall|sched-stall|lock-order|page.fault|Panicked|No space|ENOMEM|EMFILE' artifacts/final2026
```

若未知 syscall 返回 `ENOSYS`，先写最小 C 复现并在 Linux 上记录参数、返回值、errno 和副作用，再实现通用语义。不要按 `rustc`/`cargo` 名字伪造成功。

## 9. 性能优化纪律

BuildStorm 只有在正确构建成功后才有时间分。优化按“测量—定位—单变量修改—相同冷启动复测”进行：

1. 固定 QEMU、镜像哈希、kernel commit、8 核和 8 GiB；
2. 每次使用全新 overlay，并清除目标目录；
3. 记录正式脚本打印的 guest `/proc/uptime` 差值，不能用宿主耗时代替得分依据；
4. 至少三轮取中位数，并记录方差；
5. 同时保存锁等待统计、调度 stall、缺页/映射计数、Ext4/page-cache 命中与写回统计；
6. 一次只改一类瓶颈，功能回归和产物哈希通过后才保留；
7. 禁止修改 `/proc/uptime`、时钟或官方脚本来缩短报告时间。

优先级通常是：消除全局锁串行化和忙等，其次减少目录/元数据重复 I/O，再改善页缓存与 mmap 写回，最后才做微小 syscall 快路径。没有完整 BuildStorm profile 前不做猜测性性能改动。

建议实验表：

| commit | arch | QEMU | image SHA-256 | run | elapsed_s | result | 关键统计 |
|---|---|---|---|---:|---:|---|---|
| 基线 | riscv64 | 版本 | 哈希 | 1 | 待测 | 待测 | 待测 |
| 基线 | riscv64 | 版本 | 哈希 | 2 | 待测 | 待测 | 待测 |
| 基线 | riscv64 | 版本 | 哈希 | 3 | 待测 | 待测 | 待测 |
